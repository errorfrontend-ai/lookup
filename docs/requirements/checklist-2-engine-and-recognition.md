## S3 — Step 3: engine hookup (Python ingest and recognize workers, installs, `POST /recognize`, basic resolve)

### Architecture

- [ ] **S3-ARCHITECTURE-01** Work passes between the API and the fingerprint engine through BullMQ queues on Valkey: the Node API enqueues and Python workers process, with one shared queue per job type (the Python `bullmq` package is the official port that runs the same Lua scripts) (supersedes blueprint §2 and §4, "Actor System Engine" and "wrapping the Python Dejavu library"). *Source:* slice-blueprint.md §2 (blueprint §2 line 18; plan D1); slice-plan-decisions-data-model.md §4 (D1), §5 (Verified facts, BullMQ), §7 (actor mapping). *Verified by:* cross-language contract test on Valkey 8: a job added by Node on a queue name is completed by the Python worker on the same queue name.
- [ ] **S3-ARCHITECTURE-02** The fingerprint engine runs only in Python workers, and Python is used only where the engine needs it: the Python service has no sign-in, portal or station-data endpoints. *Source:* slice-plan-decisions-data-model.md §4 (D1). *Verified by:* code review of `services/fingerprinter`: no HTTP endpoint for sign-in, portal or station data.
- [ ] **S3-ARCHITECTURE-03** Fingerprinting never runs inside the API process or on the request path: `apps/api` holds no audio-decoding or fingerprint code, it hands the clip to a worker through the `recognize` queue and waits, and its event loop stays responsive while recognitions are queued (keeps blueprint §4). *Source:* slice-blueprint.md §7 (blueprint §4 line 75); slice-plan-decisions-data-model.md §4 (D1), §6 (Holds). *Verified by:* code and dependency check of `apps/api`; load test: the API keeps answering other routes while recognitions are queued.
- [ ] **S3-ARCHITECTURE-04** The blueprint's Recognition Supervisor actor is the API's `RecognitionService`, which owns admission, circuit breaking, enqueueing and waiting (supersedes blueprint §4 "Recognition Supervisor Actor"). *Source:* slice-blueprint.md §7 (blueprint §4 lines 82–86, 109); slice-plan-decisions-data-model.md §7 (actor mapping). *Verified by:* unit tests of `RecognitionService`, one per duty.
- [ ] **S3-ARCHITECTURE-05** Schedule evaluation runs inside the request as SQL (the resolve function) plus TypeScript policy in the API; there is no scheduler queue, worker or service (supersedes blueprint §4 "Campaign Scheduler Actor"). *Source:* slice-blueprint.md §8 (blueprint §4 lines 99–103, 113); slice-plan-decisions-data-model.md §7 (actor mapping). *Verified by:* code check: after the worker result the recognize path makes no further queue hop; resolution test shows the decision made inside the request.
- [ ] **S3-ARCHITECTURE-06** `recognize` and `ingest` are separate queues served by separate worker pools, so bulk ingestion can never starve recognition (keeps blueprint §4 "decouples ingestion from heavy recognition computation"). *Source:* slice-plan-recognition.md §6 (plan §Recognition flow step 5; §Target architecture); slice-blueprint.md §7; slice-plan-decisions-data-model.md §7. *Verified by:* integration and load test: with the `ingest` queue full of slow jobs, a recognize job is still picked up and answered inside its deadline, and recognition latency holds while a batch of ads is ingested.
- [ ] **S3-ARCHITECTURE-07** Any number of stateless worker processes may consume the `recognize` queue at once, and each job is handled by exactly one of them (supersedes blueprint §4 "load balancing" and "allocates an available worker actor from the pool"). *Source:* slice-blueprint.md §7 (blueprint §4 lines 84, 91–92, 109, 111). *Verified by:* integration test with two workers: N jobs give N results and no job is processed twice.
- [ ] **S3-ARCHITECTURE-08** The clip arrives as one multipart upload of the whole recording, not as a stream (supersedes blueprint §4 "audio stream buffer"). *Source:* slice-blueprint.md §7 (blueprint §4 line 83; plan §Target architecture "one POST"). *Verified by:* API end-to-end test posts a complete file part and gets the result in the same response.
- [ ] **S3-ARCHITECTURE-09** The listener app uploads audio and the backend computes the fingerprint; the app never computes or sends fingerprints (kept from blueprint §1 and §8). *Source:* slice-blueprint.md §1 (blueprint §1 line 9, §8 line 281). *Verified by:* contract test: the recognize request schema has an `audio` part and no hash field; code search: the app source contains no fingerprint code.
- [ ] **S3-ARCHITECTURE-10** No listener-facing endpoint returns a list of ads (D8). *Source:* slice-plan-decisions-data-model.md §4 (D8). *Verified by:* API route inventory test: the only listener routes are installs, recognize, choice, engagements, the stations list and client errors.
- [ ] **S3-ARCHITECTURE-11** No listener-facing credential can create, change or delete a station's ads, action cards, campaigns or schedules (kept from blueprint §3.1 "read-only payload consumption"). *Source:* slice-blueprint.md §4 (blueprint §3.1 line 57). *Verified by:* API test: an install token sent to every portal write route is answered 401 or 403.

### Engine

- [x] **S3-ENGINE-01** The engine is the in-house Python package `lookup_fingerprint` (plan name `lookup_fp`) in `services/fingerprinter`, implementing the landmark algorithm on spectral peaks from the Fast Fourier Transform (supersedes blueprint §2 and §4 "Dejavu"). *Source:* slice-blueprint.md §2 (blueprint §2 line 17; plan D9); slice-plan-decisions-data-model.md §4 (D9). *Verified by:* pytest: an excerpt of a reference recording is matched to that reference. *Evidence:* services/fingerprinter/tests/test_matching.py :: test_phone_clip_matches_right_ad_and_offset.
- [ ] **S3-ENGINE-02** The engine provides its four core parts (fingerprinting, alignment, the database index and the decoder) as its own modernised modules, each with unit tests (D9 replaces "vendor Dejavu's files"). *Source:* slice-plan-decisions-data-model.md §5 (Verified facts, Dejavu unmaintained; D9). *Verified by:* repository check: a module for each part exists and each has unit tests. *(partly built)* *Built so far:* `decode.py`, `fingerprint.py`, `matcher.py`, `index.py` and `config.py` with tests in `services/fingerprinter/tests/` (status-built.md §9); a separate alignment module with its own tests is not shown.
- [ ] **S3-ENGINE-03** The Dejavu package is never a dependency and no Dejavu source file is copied into the repository. *Source:* slice-blueprint.md §2 (plan D9; memory/look-up-project-decisions.md); also stated for every phase in slice-plan-decisions-data-model.md §4 and §5 (tagged ALL). *Verified by:* dependency check: `services/fingerprinter/pyproject.toml` lists no Dejavu package; code search finds no Dejavu file.
- [ ] **S3-ENGINE-04** SoundFingerprinting, Olaf and audfprint are benchmark baselines only and never runtime dependencies. *Source:* slice-blueprint.md §2 (plan D9); also slice-plan-decisions-data-model.md §4 (tagged ALL). *Verified by:* dependency check of the worker's runtime requirements.
- [ ] **S3-ENGINE-05** The engine does not use the deprecated `scipy.ndimage.filters` module. *Source:* slice-plan-decisions-data-model.md §5 (plan §Verified facts, line 245). *Verified by:* code scan finds no import of `scipy.ndimage.filters`; the test suite runs with deprecation warnings from that module treated as errors.
- [x] **S3-ENGINE-06** Every audio input, reference ads and listener clips alike, is resampled to one canonical sample rate before fingerprinting; audio is never fingerprinted at its file's native rate. *Source:* slice-blueprint.md §2 (plan D9, Verified facts sample-rate trap); slice-plan-decisions-data-model.md §4 (D9), §5 (sample-rate trap). *Verified by:* engine test: a 16 kilohertz phone-like clip matches a 44.1 or 48 kilohertz reference of the same audio, and skipping the resampling breaks matching. *Evidence:* services/fingerprinter/tests/test_matching.py :: test_skipping_resampling_breaks_matching ; services/fingerprinter/tests/test_decode.py :: test_decodes_phone_aac_to_canonical_rate.
- [ ] **S3-ENGINE-07** Hashes are exact packed integers (no truncated or text hashes) stored in the `bigint` column `fingerprints.hashes_version_1.hash` (supersedes blueprint §6 `hash BYTEA`). *Source:* slice-blueprint.md §2 (blueprint §6 line 200; plan D9); slice-plan-decisions-data-model.md §4 (D9). *Verified by:* engine unit test: packing then unpacking a landmark returns the same frequency pair and time difference; database test: the column type is `bigint`. *(built, not yet tested)* *Built in:* services/fingerprinter/lookup_fingerprint/fingerprint.py (64-bit packing); Foundation migration (hash table).
- [ ] **S3-ENGINE-08** The hash lookup is vectorised: one query per clip of the form `hash = ANY($1)` against `fingerprints.hashes_version_1`, with the hashes passed as a bound parameter, never one query per hash and never with hash values written into the SQL text. *Source:* slice-blueprint.md §2 (plan D9 "vectorised lookup"); slice-plan-decisions-data-model.md §4 (D9); slice-plan-recognition.md §8 (plan §Recognition flow step 7, line 504). *Verified by:* engine or worker test against Postgres with a statement counter: one lookup statement per clip, with the hashes as a parameter.
- [ ] **S3-ENGINE-09** Peak picking uses an amplitude floor relative to the clip's own level, not an absolute level, so quiet phone recordings still produce peaks. *Source:* slice-blueprint.md §2 (plan D9); slice-plan-decisions-data-model.md §4 (D9). *Verified by:* engine test: the same clip at much lower gain yields a comparable number of hashes and still matches.
- [x] **S3-ENGINE-10** A match needs at least T aligned hashes; below that threshold the answer is no match. *Source:* slice-plan-recognition.md §8 (plan §Recognition flow step 7, line 505); slice-blueprint.md §2 (plan D9, G14). *Verified by:* engine test with T = 7: 6 aligned hashes (T − 1) give NO_MATCH, and 30 aligned hashes with no runner-up give MATCH. Verification reworded in review round 1 to the cases the test has.
- [x] **S3-ENGINE-11** A match also needs the margin between the best and the second-best candidate to be at least R (top-2 margin); when two assets share audio (a jingle) the answer is AMBIGUOUS, never a confident wrong brand. *Source:* slice-plan-recognition.md §8 (plan §Recognition flow step 7; G14); slice-blueprint.md §2 (plan D9); slice-plan-decisions-data-model.md §4 (D9), §6 (G14). *Verified by:* engine test: two references share a jingle; a clip of the shared part has enough aligned hashes but a margin below R and is not a match. *Evidence:* services/fingerprinter/tests/test_matching.py :: test_decide_threshold_and_margin[<five cases>] ; services/fingerprinter/tests/test_matching.py :: test_shared_audio_is_ambiguous_not_a_wrong_brand.

### Capture time and receipt time

- [ ] **P4-TIMERULE-01** Every recognition keeps two separate times, `captured_at` (when the clip was heard, normalised by the server) and `received_at` (when the server first got it), and the server never substitutes one for the other. *Source:* slice-plan-recognition.md §1 (plan §Recognition flow, time rule, lines 470–472; §Data model row recognition_events). *Verified by:* API end-to-end test: a deferred clip captured two hours before it is sent produces a row whose two times differ by about two hours.

- [ ] **P4-TIMERULE-03** Which stations are in-window candidates is decided at the capture time, not the receipt time. *Source:* slice-plan-recognition.md §1 (plan §Recognition flow, time rule; step 8, line 509). *Verified by:* database test with two stations whose windows differ: the in-window set for a deferred clip equals the set whose windows contained the capture time.

## Possible gaps in the sources (S3 and P4)

These are places where the sources are silent, vague or in conflict. Nothing below has been turned into a requirement; each needs a decision before or during the phase. The slice gap it comes from is named in brackets.

### Phase homes and build order

1. **Phase homes are judgement calls.** Near-full acoustic duplicates, partial overlap to NEEDS_REVIEW and re-index tooling sit in P8; the local in-flight limit, the deferred-clip rules and both k6 tests sit in P4; the breaker's half-open test and ingest retries with backoff sit in S3; the candidate filters and the window rule sit in S3 while grace sits in P4. The super-admin overlap review (P5A) has nothing to review until P8. The user should confirm these homes. (recognition gap 1; blueprint gap 19; data-model gap 30; cross-cutting gap 7)
2. **The k6 load tests have no targets and no clear home.** No target request rate or 95th-percentile latency is given, O14 waits for a "Phase 3 load test" that no phase names as a deliverable, and it is not stated whether the 4-processor build machine can run it or whether it belongs with the P8 tests on Render. (recognition gaps 1, 11; blueprint gap 18; cross-cutting gap 21)
3. **Repeated keys and capture time in Step 3.** No source says what Step 3 does with a repeated idempotency key before the P4 claim exists (replay, 409 or something else; it must not be a database error). Nor does any source say what Step 3 stores as `captured_at` before clock correction exists: the built check already enforces the 24-hour and 2-minute bounds, so a raw time from a phone with a wrong clock would fail the insert. (recognition gap 2; blueprint gap 25)
4. **Device-integrity verdict.** Resolved in review round 1: reading and storing are both S3 (S3-INSTALLS-10 to -12). The verdict values and what, if anything, a failed verdict changes are still not stated. (data-model gap 31)

### Contract and names

5. **Wire names against the naming rule.** The plan's request, job, worker-result and response names (`clip_ms`, `offset_ms`, `audioB64`, `fpVersion`, `asset_key`, `deferred`, `w`, `h`) break the newer "no abbreviations, units in the name, booleans as questions" rule, and no source gives the final names. The worker files are `match.py` and `ingest.py` in the master plan, while Step 3 calls the job `recognize`; the image commands are `match` and `ingest`. (recognition gap 3; blueprint gap 15; data-model gaps 10, 12)
6. **No station identifier in the response.** The result and candidate shapes give a station's name, frequency and logo only, and G9 calls the tenant id a leak, yet the choice endpoint, the engagements endpoint and the station hint all need a station identifier from the app. Review round 1 added the requirement for one public reference (S3-RESPONSE-17); whether it is the station id or an opaque candidate token must still be chosen. (recognition gap 4; blueprint gap 13; data-model gap 21)
7. **`result.kind` is undefined.** Its values are never listed, and no source says how a default-card result is marked to the app, although the stored outcome is `MATCH_DEFAULT` and the public `status` has only three values. (recognition gap 5; data-model gap 29)
8. **Images in the response.** How header-image and logo addresses are served from a private bucket (a public delivery path, or signed addresses and their lifetime) is not stated; replays and saved History entries need them to keep working. (recognition gap 30)
9. **Codec list and versions.** The allowed `codec` values are not listed; the edge accepts `OggS` while the app records AAC only; the behaviour when a job's fingerprint version differs from the worker's is not stated. (recognition gap 31)
10. **Contract tooling.** A JSON Schema for a multipart recognize request is unusual and its use is not explained; nothing says how the Dart and Python sides stay in step with the schemas beyond shared fixtures. (data-model gap 36)

### Errors and status codes

11. **Missing error details.** No code names for 413 and 415; no status or code for a clip length outside 2 to 15 seconds, a missing or malformed field, or a station hint naming an unknown station; whether `Retry-After` accompanies `RECOGNITION_TIMEOUT` and 429 is not stated. (recognition gap 6; blueprint gap 24)
12. **What counts as `INVALID_AUDIO`.** Which failures map to 400 `INVALID_AUDIO` (decode failure, no audio stream, too short after decoding, silence) and which to 415 or a server error is not listed. (recognition gap 7)
13. **Replaying a stored `INVALID_AUDIO`.** It is terminal, and terminal outcomes are "replayed with 200", yet the first answer was a 400. (recognition gap 8)
14. **Worker result values.** The worker's `status` values are not listed (match, no match, ambiguous, expired, error codes), nor what the API answers and stores when the worker returns `EXPIRED` or a lookup-timeout code. (recognition gap 9)
15. **The client acknowledgement rule is incomplete.** It covers 200, 422, `INVALID_AUDIO`, 409, 429, 503 and network errors, but not 401 (re-register and retry?), 413, 415, 426, other 400s or 500; the server's choice of codes affects it. (recognition gap 23)
16. **Refused requests.** Whether requests refused before the claim (401, 413, 415, 429) are recorded anywhere beyond the logs is not stated. (recognition gap 33)

### Numbers

17. **Engine numbers before the pilot.** T, R, the canonical sample rate, the hash-count tolerance and the final hash type were left to Phase 0, whose field testing D10 moved to the pilot. The engine's current values (20 aligned landmarks, margin 2, 11,025 hertz) are starting points; no source records the interim values to ship with before P8. (recognition gap 10; data-model gap 34; cross-cutting gap 13)
18. **Numbers not given at all.** The queue-depth threshold; the local in-flight limit; the breaker's failure threshold, reset time and half-open trial count; the heartbeat interval and expiry; the `Retry-After` value for live 503s (the Busy wireframe shows "Trying again in 12 s"); the "margin" in "2.5 seconds plus margin"; the presigned GET lifetime; the install-token lifetime; the per-address ceiling; the deferred priority value; and the ingest retry count and delays. The live limits (6 per minute, 60 per day) and the deferred limit (10 per hour) are examples only. (recognition gap 11; blueprint gap 18)
19. **256 kilobytes.** Not stated whether this is 256,000 or 262,144 bytes, or whether it limits the audio part or the whole multipart body. (recognition gap 12)

### Time rules and windows

20. **Time-bound details.** The 24-hour and 2-minute bounds are introduced under "Deferred:", but the database check applies to every row; whether live requests get the same 422 answers, whether each bound includes its exact instant, and how a missing, malformed or absurd `sent_at` (for example earlier than `captured_at`) is treated are not stated. Upload time on a slow network is counted as clock skew. (recognition gap 13)
21. **Which rate allowance.** Not stated which allowance a request uses when the app says live but the server computes deferred (or the reverse), or whether replays, 409 answers and retries after a 503 use up the allowance; at 6 per minute, automatic retries could lock a listener out. (recognition gap 14)
22. **Window edge rules.** Not stated: whether window and period boundaries are inclusive; which ISO day a midnight-crossing window belongs to after midnight (the data-model slice's test assumes the start day); behaviour across daylight-saving changes for stations outside Zambia; and whether equal start and end times mean "all day" (the built table refuses them). (recognition gap 29; blueprint gap 23)

### Resolution

23. **Candidate and owner definitions.** Step 8 filters candidates by ACTIVE station and campaign, then re-checks status "at `received_at`". Status keeps no history, so if candidates are filtered by current status the later check can never fail, and a campaign paused after capture (O13) would not be a candidate at all. "Owner" is never defined: whether it needs an ACTIVE campaign, a READY ad and an ad that is not archived is not stated. (recognition gap 15)
24. **Suspended station against the default-card rule.** Step 8 says a station no longer active at receipt gets "the default card"; the Phase 4 check and the baseline say a suspended station's card is never returned. This checklist assumes no card at all for a station that is not ACTIVE. (recognition gap 16)
25. **No default card in the full cascade.** Not stated what happens when the hinted owner has no default card, when some chooser candidates have none, or when a campaign is at its limit or paused and the client has no default card. (recognition gap 17)
26. **Chooser order and overflow.** With more than four in-window stations, which four are shown and in what order is not stated; "most recently aired first" has no definition without air-play data (latest window end, latest recognition, or something else). (recognition gap 18)
27. **Resolution values.** Not every case maps to one of the five values (default card by hint, default card for a single owner, chooser before a choice); the built `recognition_events` has no `resolution` column yet. (recognition gap 19)
28. **What an engagement limit counts, and when.** Step 8 "reserves the cap atomically" at recognition time; O4 and the race test count taps. Not stated whether the counter moves at recognition, at the tap or both, whether chooser candidates each reserve, or whether taps on a default card count. A money budget (blueprint "budget cap") is silently dropped. (recognition gap 20; blueprint gap 8)
29. **Out-of-window policy values.** The data model gives campaigns an `out_of_window` policy, but O3 states one fixed behaviour and no source lists other values. (recognition gap 28; data-model gap 18)

47. **Partition columns for candidates and engagements.** The conventions require tables that grow with listener traffic to be partitioned by month on their arrival time (P4-DATABASE-03), but the plan's data model gives `recognition_candidates` no time column and `engagement_events` only `occurred_at` (clamped, so not the arrival time). The arrival column of each, and how the cross-month uniqueness table of P4-ENGAGEMENTS-12 is cleaned up, are not stated.
48. **Super-admin read path into the fingerprint schema.** G3 makes the `fingerprints` schema readable only by the worker role, while O6 and plan §B let super admins see shared-audio links and play both assets of a partial overlap. Whether `lookup_admin_api` gets a narrow SECURITY DEFINER function (returning the finding, the two asset numbers and short-lived preview keys) or a `SELECT` grant on the overlap table only is not decided; ADR-002 should record the choice (conflict 14).
49. **Decode caps for ingest.** Baseline §4 requires time and size caps on all audio decoding; the plan gives values only for listener clips (1-second decode, 256 KB). The time cap, the input-size cap (uploads may be 20 MB) and the decoded-length cap for ad uploads are not stated (S3-INGEST-24).
