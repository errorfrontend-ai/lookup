Written on 20 October 2026, **before any code**, from the project owner's request of 19 October 2026 and the approved plan,
as [ADR-005](../adr/ADR-005-listener-accounts.md) and [the design](../design/listener-accounts.md) record them. Nothing is built
yet, so nothing is ticked. An item is ticked only with a named test as *Evidence:* (`npm run check:requirements`).

- *Source:* "ADR" is ADR-005 and "design" is `docs/design/listener-accounts.md`; "baseline" is `docs/security-baseline.md`;
  "global rules" are the error-handling, logging and tests rules in the owner's CLAUDE.md.

## LA-GATE — the result waits for the account

- [ ] **LA-GATE-01** With `LISTENER_ACCOUNT_REQUIRED` on, a scan of an ad (a match, a default card or a "Which station?" chooser) from an install with no account is answered `{ status: 'ACCOUNT_REQUIRED', recognition_id, request_id, is_deferred, captured_at }` and nothing else: no station, client, title, card, candidate or logo. *Source:* ADR decision 2; design LA-D1. *Verified by:* API end-to-end test per kind of answer: the body has exactly those five fields and passes the contract.
- [ ] **LA-GATE-02** `NO_MATCH` and every error answer are unchanged by the gate. *Source:* design LA-D2. *Verified by:* API test: a clip nothing matches, an invalid clip and a busy answer are the same with the switch on and off.
- [ ] **LA-GATE-03** The scan is recognised and recorded exactly as before: the outcome, station, campaign and card are stored, and the station's figures count it. *Source:* design LA-D3. *Verified by:* API test: after a gated scan the recognition row holds the same outcome and station as an ungated one, and the station's listener figures count it.
- [ ] **LA-GATE-04** The answer to a finished idempotency key (a replay, a retry after a lost answer) is gated the same way, so resending a clip never gets the card. *Source:* design §1 fact 3, LA-D1. *Verified by:* API test: send a clip, then the same key again, both answered `ACCOUNT_REQUIRED`; then sign up and send the key again: the card.
- [ ] **LA-GATE-05** With the switch off, every answer is exactly as before this change. *Source:* design LA-D14. *Verified by:* the existing recognize, deferred and replay suites pass unchanged with the switch off; one case compares an answer with the switch off against a stored fixture.
- [ ] **LA-GATE-06** Reveal: `GET /api/v1/recognitions/:recognitionId` gives the owning install, once it has an account, the full answer the scan would have had (same recognition id, status, card versions and chooser order, minus any station no longer ACTIVE). An install with no account still gets `ACCOUNT_REQUIRED`. Another install's recognition and an unknown id answer the same 404. A malformed id answers 400 naming the field, never the value. *Source:* design LA-D12. *Verified by:* API tests for each case, including a second install with its own account.
- [ ] **LA-GATE-07** A clip sent later from the outbox (`is_deferred`) is gated the same way; the app treats `ACCOUNT_REQUIRED` as a final answer (the clip is deleted, no retry) and keeps a History row. *Source:* design §3.2 point 5. *Verified by:* API test of a deferred send; Flutter test of the deferred sender and History row.
- [ ] **LA-GATE-08** Once the switch is on, the station-choice and report routes answer an install with no account like an unknown recognition (404). A button tap is unchanged. *Source:* design LA-D13. *Verified by:* API tests: an account-less install gets the same 404 for a real recognition id and an invented one; with an account the routes work as before.

## LA-ACCOUNT — email, code, details

- [ ] **LA-ACCOUNT-01** Asking for a code answers 202 for any well-formed email, known or not; the body and timing class are the same, so the answer never says whether an account exists. *Source:* ADR decision 3; design §4. *Verified by:* API test: a known and an unknown email get byte-identical bodies and headers.
- [ ] **LA-ACCOUNT-02** A code is 6 random digits, lasts 10 minutes, locks after 5 wrong tries, and a new one can be asked for once a minute (`RESEND_TOO_SOON` with `Retry-After`). It is kept only as a keyed hash bound to the email and works only for the email it was sent to. *Source:* design §4, LA-D5; the station code pattern (P5A-VERIFICATION-01..05). *Verified by:* API tests: right, wrong, expired, locked, resent too soon, a code used for another email, a code used twice.
- [ ] **LA-ACCOUNT-03** A right code for an email that has an account links this install to it and answers `SIGNED_IN`; for a new email it answers `DETAILS_NEEDED` with a ticket. *Source:* design §4, LA-D6. *Verified by:* API tests of both answers; a second install signing in to the same account.
- [ ] **LA-ACCOUNT-04** The ticket is signed, lasts 10 minutes, is tied to this install and this email, and is stored nowhere. A forged, expired, other-install or other-email ticket is refused with `ACCOUNT_TICKET_NOT_VALID`. *Source:* design LA-D6. *Verified by:* API tests for each refusal.
- [ ] **LA-ACCOUNT-05** Creating the account needs a valid ticket, a gender from the four values, a whole age from 13 to 99 and the current consent wording. A body with anything else (unknown field, age 12 or 100 or 30.5, gender "X", no consent, old wording) is refused naming the field and the reason, never the value; age under 13 gets `ACCOUNT_AGE_TOO_YOUNG`. *Source:* design LA-D7, LA-D8. *Verified by:* API tests at ages 12, 13, 99, 100 and for each bad field.
- [ ] **LA-ACCOUNT-06** The stored birth year is the current year minus the age, the consent wording and time are stored, and the email is stored as a keyed hash (unique) plus a sealed copy; no plain email is in any column. *Source:* design LA-D7, LA-D11, §5. *Verified by:* database assertions after sign-up; the sealed value opens only with the key and the account id.
- [ ] **LA-ACCOUNT-07** An install has at most one account: signing in to, or creating, a different account on an install that already has one is refused with `ALREADY_SIGNED_IN`; the same account again changes nothing. *Source:* design §4. *Verified by:* API tests.
- [ ] **LA-ACCOUNT-08** If a ticket is valid but the email gained an account meanwhile, the install is linked to that account and the answer is `SIGNED_IN`; two creations at once make one account. *Source:* design §4. *Verified by:* API test with two concurrent creations.
- [ ] **LA-ACCOUNT-09** Sign-out unlinks only this install; the account and its other installs are untouched. *Source:* ADR decision 6. *Verified by:* API test.
- [ ] **LA-ACCOUNT-10** Deleting the account erases the email (hash and sealed copy), gender, birth year and consent record, and unlinks every install of the account; it answers 204 also when there is no account. Recognition rows stay. An audit row records the action without any personal value. *Source:* ADR decision 6. *Verified by:* API and database tests; a later sign-up with the same email makes a new account.
- [ ] **LA-ACCOUNT-11** `GET /api/v1/listener-account` returns whether the install is signed in and the email only in masked form (first character, stars, domain). *Source:* design §4. *Verified by:* API test: the response never holds the full address.

## LA-ROUTES — the new routes meet the baseline

- [ ] **LA-ROUTES-01** Every listener-account route needs the install token (401 first), then the update gate (426), then its own allowance; strict zod body; it is listed in `LISTENER_ROUTES`; a portal cookie opens none of them; and the open-routes inventory test lists exactly them. *Source:* baseline §2 and §3 (listener rows); S3-INSTALLS-02 as rewritten; design §4. *Verified by:* the open-routes test in `listener-installs.test.ts` (updated); per-route tests for 401, 426 and cookie refusal.
- [ ] **LA-ROUTES-02** Allowances are enforced and counted by keyed hash: codes 3 an hour per email and 10 a day per install; code checks 20 an hour per install; creations 5 a day per install; the rest share the follow-up allowance. Past a limit: 429 in the error envelope with `Retry-After`. When the counter store is down the routes refuse (503), never allow. *Source:* design §4; baseline §2 (rate limits). *Verified by:* API tests for each limit and for the store being down.
- [ ] **LA-ROUTES-03** Every failure path of every new route answers in the error envelope with the request id and a plain message, and a leak test asserts the response holds no exception class name, SQLSTATE, "Fatal error", file path or stack trace. *Source:* global rules (two layers; ALL-TESTS-05). *Verified by:* `error-responses` style test over each new route's failures, including the database and key-value store being down.
- [ ] **LA-ROUTES-04** The new error codes are in the catalogue with plain messages and contract fixtures, and the codes the outbox can meet have rows in the outbox rules. *Source:* design §4. *Verified by:* `error-envelope-fixtures.test.ts` and `listener-outbox-rules.test.ts` pass with them.
- [ ] **LA-ROUTES-05** The code email is queued with five tries and a 10-minute delivery deadline; the address is never logged (recipients are named by keyed hash); the job's data is removed when done or failed. *Source:* design §4, §6; baseline §3 (station codes). *Verified by:* notification tests; log-capture test.

## LA-DATABASE — storage

- [ ] **LA-DATABASE-01** `app.listener_accounts` exists with row-level security on and no policy and no grant for `lookup_api`; the API role reads and writes it only through the listed definer functions. *Source:* ADR-002; design §5; security-by-design memory. *Verified by:* `database-catalogue.test.ts` (updated lists), `database-privileges.test.ts`: as `lookup_api`, `SELECT`, `INSERT`, `UPDATE`, `DELETE` on the table are each refused.
- [ ] **LA-DATABASE-02** `listener_installs.listener_account_id` is a nullable foreign key (`ON DELETE SET NULL`) with an index, and the API role cannot write it directly. *Source:* design §5, LA-D4. *Verified by:* catalogue and privileges tests.
- [ ] **LA-DATABASE-03** Each new definer function pins `search_path`, is owned by the schema owner, is granted to the API role only, and returns only what its caller needs (never the sealed email except to the one describe function). *Source:* baseline §1 (definer rule). *Verified by:* `database-privileges.test.ts` cases per function.
- [ ] **LA-DATABASE-04** The migration is new (no released migration edited), named and constrained by `docs/conventions.md`; the catalogue test's list of allowed binary columns gains the keyed email hash and the sealed email, and S3-PRIVACY-01's wording says so while still proving no clip can be stored. *Source:* ALL-MIGRATIONS-01..04; ALL-DATABASE rules; S3-PRIVACY-01. *Verified by:* `database-catalogue.test.ts`, `source-scan.test.ts` (digest list untouched).

## LA-PRIVACY — personal data

- [ ] **LA-PRIVACY-01** The email, code, ticket, gender, age and birth year appear in no log line and no error response, whatever fails. The log `actor` stays the keyed hash of the install. *Source:* global rules ("never log PII"); baseline §7. *Verified by:* `log-privacy.test.ts` cases over a whole sign-up, a failed sign-up and a deletion, reading captured logs.
- [ ] **LA-PRIVACY-02** The app's privacy wording is rewritten: S4-PERMISSION-10's list item and the Privacy screen say stations see how many people used their buttons and the mix of ages and genders, never a name or an email, and say what the app asks for and why. *Source:* ADR "What this supersedes". *Verified by:* widget tests find the new words on the Permission and Privacy screens.
- [ ] **LA-PRIVACY-03** The sign-up shows a consent line the listener must tick before **Create account** works; the server stores the wording's version and the time, and refuses an unknown version. *Source:* design LA-D8; P8-DATA-PROTECTION-03 (consent points). *Verified by:* widget test (the button is disabled until ticked); API test.
- [ ] **LA-PRIVACY-04** The app writes no email, code, gender or age to the device log or to a crash report, and its personal-data scrubber removes an email-shaped value from reports. *Source:* S4-PRIVACY-04; global rules. *Verified by:* Flutter tests (`personal_data_scrubber_test.dart` extended, development-log test); the emulator run's device-log check after the account journey.
- [ ] **LA-PRIVACY-05** No station-facing, advertiser-facing or admin response holds an email, a gender or an age of a person, or any listener identifier: only counts of groups (ALL-PRIVACY-01 as rewritten). *Source:* ALL-PRIVACY-01; ADR decision 5. *Verified by:* contract tests of every station route that carries the mix; a scan of the portal API responses for the listener fields.
- [ ] **LA-PRIVACY-06** Phase 8's data-protection work is extended to listeners and recorded: controller registration, privacy notice, consent wording, the Google Play data-safety form (email, gender, age) and the s.70 / Frankfurt question. *Source:* ADR "Consequences"; P8-DATA-PROTECTION-01..07. *Verified by:* P8 checklist items name listeners (a review at the P8 gate).

## LA-STATS — who is listening

- [ ] **LA-STATS-01** The mix counts **distinct listeners** (one per account; one per install with no account) who identified the station's ads in the range, by gender and by age band, plus the number not known yet; a person with two installs counts once. *Source:* design §7. *Verified by:* API tests with seeded accounts, installs and recognitions.
- [ ] **LA-STATS-02** The age bands are under 18, 18–24, 25–34, 35–44, 45–54 and 55 and over, from the stored birth year at query time, with the boundary years tested. *Source:* design LA-D9. *Verified by:* API tests at each boundary.
- [ ] **LA-STATS-03** Small-group rule: below 10 known listeners no breakdown is returned; otherwise a group of 1–9 is merged into "Other groups", the smallest shown group joins when only one group would be hidden or the merged number is under 10, and a zero is shown as 0. *Source:* design LA-D10, §7. *Verified by:* unit tests of the rule at 9, 10 and 11 and for each case; an API test.
- [ ] **LA-STATS-04** There are two separate breakdowns and never a gender × age grid or any per-person row. *Source:* design LA-D10. *Verified by:* contract test of the response shape.
- [ ] **LA-STATS-05** A station reads the mix of its own recognitions only (row-level security); another station's ad id answers 404; the ranges 1, 7 and 30 days work as for the listener figures. *Source:* P5B-D2 isolation; design §7. *Verified by:* `station-isolation-matrix`-style tests; API tests for the ranges.
- [ ] **LA-STATS-06** Signing out, or deleting the account, moves that phone's scans to "not known yet"; signing in again restores them. *Source:* design LA-D15. *Verified by:* API test.
- [ ] **LA-STATS-07** The portal's **Who is listening** section (Overview and each ad's Overview tab) shows loading, error, empty, "not enough listeners yet" and normal states; bars with a Chart/Table switch and the range switch; the not-known-yet number; one column on a phone; labelled controls; keyboard and screen-reader friendly. *Source:* design §7; P5B-OVERVIEW rules; ALL-USABILITY-01, -02. *Verified by:* portal component tests per state (axe check); the Playwright journey where the machine allows.

## LA-APP — the listener app

- [ ] **LA-APP-01** The app reads `ACCOUNT_REQUIRED` strictly and moves to `AccountRequiredState`, which shows the gate screen and never a card, station or client. *Source:* design §3.3. *Verified by:* parser test with the contract fixture; recognition-flow test; the compiler's exhaustive switches.
- [ ] **LA-APP-02** The gate screen shows its heading, one plain sentence, **Create account**, **I already have an account** and **Not now**, with the layout rules of the other flow screens. *Source:* design §3.1. *Verified by:* widget test and golden images (320, 360, tablet; light, dark).
- [ ] **LA-APP-03** Email step: email keyboard and autofill, a not-an-email message in plain words, **Send me a code**, a "too many tries" and a "no connection" state. *Source:* design §3.1. *Verified by:* widget tests per state.
- [ ] **LA-APP-04** Code step: six digits, one-time-code autofill, a 60-second countdown before **Send a new code**, **Change email**, and separate words for wrong, expired and locked codes. *Source:* design §3.1. *Verified by:* widget tests per state, with a controlled clock.
- [ ] **LA-APP-05** About-you step: four gender chips, an age box that accepts 13–99 and says why otherwise, a consent checkbox linking to Privacy, and **Create account** pinned above the keyboard; under 13 shows the kind message and creates nothing. *Source:* design §3.1, LA-D7. *Verified by:* widget tests including a keyboard-open layout test at 320 × 568.
- [ ] **LA-APP-06** After sign-up or sign-in the app asks for the reveal and then shows the usual result, fallback or chooser screen, saved to History as before. *Source:* design §3.2 points 2–3. *Verified by:* app journey test (gate → sign-up → result; gate → sign-in → chooser → result).
- [ ] **LA-APP-07** A returning email (the code step answers `SIGNED_IN`) skips the about-you step. *Source:* design §3.2 point 3. *Verified by:* app journey test.
- [ ] **LA-APP-08** **Not now** returns to Home and History keeps a "Sign up to see this result" row (no card), which reopens the gate for that recognition. *Source:* design §3.2 point 4. *Verified by:* app journey test; History store test.
- [ ] **LA-APP-09** An outbox answer of `ACCOUNT_REQUIRED` deletes the clip, writes the History row, posts the existing generic notification, and its tap opens the gate. *Source:* design §3.2 point 5. *Verified by:* `deferred_result_handler_test.dart`, `notification_launch_handler_test.dart`, sender test.
- [ ] **LA-APP-10** With no connection at any account step the app says so, keeps the scan and lets the listener try again; nothing technical is shown. *Source:* design §3.2 point 6; S4 rules (no technical text). *Verified by:* widget tests with the no-technical-text helper.
- [ ] **LA-APP-11** Settings → Account shows the masked email, **Sign out** and **Delete my account** (a confirm sheet saying what is erased) when signed in, and **Create account** and **Sign in** when not; it reads the state from the server and survives being offline. *Source:* design §3.1. *Verified by:* widget tests; journey test.
- [ ] **LA-APP-12** Every new word is a key in `app_en.arb` with its description; no word is written in Dart; no colour or duration outside the tokens. *Source:* docs/conventions.md; P6-LOCALISATION-01..02. *Verified by:* `source_scan_test.dart`, the l10n test.
- [ ] **LA-APP-13** The new screens meet the app's layout rules: 48 dp targets, 8 dp gaps, 320 dp to the tablet column, both themes, reduced motion, text scale 200% without clipping, focus order and semantic labels. *Source:* S4/P6 UX rules; ALL-USABILITY. *Verified by:* widget and golden tests; the accessibility test used for the other screens.
- [ ] **LA-APP-14** The structure tests allow exactly the new `features/account/` folder with its three layers, and the layer-import rules still hold. *Source:* design §3.3. *Verified by:* `feature_folders_test.dart`, `layer_imports_test.dart`.
- [ ] **LA-APP-15** The Python stand-in API serves the new routes and the emulator driver runs the whole journey (gate, sign-up from the Mailpit-like code, result, Settings, sign out) against the release APK. *Source:* S4/P6 emulator rules. *Verified by:* `tool/run_emulator_tests.py` run with Docker closed.
- [ ] **LA-APP-16** The app version is raised and the server's minimum is set to it when the switch goes on, so an old app meets the update screen. *Source:* design §8. *Verified by:* `listener-app-version-gate.test.ts` case; app version test.

## LA-ROLLOUT — switching it on safely

- [ ] **LA-ROLLOUT-01** `LISTENER_ACCOUNT_REQUIRED` is a validated setting that defaults to off; with it off the account routes still work and nothing else changes. *Source:* design LA-D14. *Verified by:* `startup-checks.test.ts`; LA-GATE-05.
- [ ] **LA-ROLLOUT-02** `LISTENER_EMAIL_ENCRYPTION_SECRET` is validated like the install pepper: the API refuses to start in production when it is missing, short, a placeholder or reused as another secret, and the message never prints it. *Source:* S3-INSTALLS-07 pattern; design §6. *Verified by:* `startup-checks.test.ts`.
- [ ] **LA-ROLLOUT-03** `.env.example`, `render.yaml`, the Render runbook and the security baseline name the new settings and secret, and the baseline's listener rows describe accounts. *Source:* design §8; baseline. *Verified by:* review at the gate; `deploy-files` tests where they exist.
- [ ] **LA-ROLLOUT-04** On the live showcase, a real email arrives through Brevo within a minute, the whole journey works on the owner's phone, and only then is the switch turned on. *Source:* design §8. *Verified by:* a recorded walkthrough in the design (not a test).
