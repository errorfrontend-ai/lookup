## LA-ACCOUNT — email, code, details

- [x] **LA-ACCOUNT-01** Asking for a code answers 202 for any well-formed email, known or not; the body and timing class are the same, so the answer never says whether an account exists. *Source:* ADR decision 3; design §4. *Verified by:* API test: a known and an unknown email get byte-identical bodies and headers. *Evidence:* apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-01: answers 202 the same way for an email with an account and one without, so it never says which has one
- [x] **LA-ACCOUNT-02** A code is 6 random digits, lasts 10 minutes, locks after 5 wrong tries, and a new one can be asked for once a minute (`RESEND_TOO_SOON` with `Retry-After`). It is kept only as a keyed hash bound to the email and works only for the email it was sent to. *Source:* design §4, LA-D5; the station code pattern (P5A-VERIFICATION-01..05). *Verified by:* API tests: right, wrong, expired, locked, resent too soon, a code used for another email, a code used twice. *Evidence:* apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-02: a code is six digits, is sent to the address typed and nowhere else, and works once ; apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-02: a second code within a minute is RESEND_TOO_SOON with a Retry-After, and after a minute it is sent ; apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-02: a code works only for the email it was sent to ; apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-02: five wrong tries lock the code; the right one is then refused, and a new code works ; apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-02: a code is useless after ten minutes
- [x] **LA-ACCOUNT-03** A right code for an email that has an account links this install to it and answers `SIGNED_IN`; for a new email it answers `DETAILS_NEEDED` with a ticket. *Source:* design §4, LA-D6. *Verified by:* API tests of both answers; a second install signing in to the same account. *Evidence:* apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-03, -04, -05, -06: a right code for a new email gives a ticket; the details make the account, linked to the install, with the email sealed ; apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-03: a right code for an email that has an account signs this install in to it, with no ticket and no questions
- [x] **LA-ACCOUNT-04** The ticket is signed, lasts 10 minutes, is tied to this install and this email, and is stored nowhere. A forged, expired, other-install or other-email ticket is refused with `ACCOUNT_TICKET_NOT_VALID`. *Source:* design LA-D6. *Verified by:* API tests for each refusal. *Evidence:* apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-03, -04, -05, -06: a right code for a new email gives a ticket; the details make the account, linked to the install, with the email sealed ; apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-04: a ticket made for another install, another email, or altered, or expired, is refused with ACCOUNT_TICKET_NOT_VALID and creates nothing
- [x] **LA-ACCOUNT-05** Creating the account needs a valid ticket, a gender from the four values, a whole age from 13 to 99 and the current consent wording. A body with anything else (unknown field, age 12 or 100 or 30.5, gender "X", no consent, old wording) is refused naming the field and the reason, never the value; age under 13 gets `ACCOUNT_AGE_TOO_YOUNG`. *Source:* design LA-D7, LA-D8. *Verified by:* API tests at ages 12, 13, 99, 100 and for each bad field. *Evidence:* apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-03, -04, -05, -06: a right code for a new email gives a ticket; the details make the account, linked to the install, with the email sealed ; apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-05: <why> is refused and creates nothing ; apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-05: age <age> (<note>) makes an account whose birth year is this year minus it
- [x] **LA-ACCOUNT-06** The stored birth year is the current year minus the age, the consent wording and time are stored, and the email is stored as a keyed hash (unique) plus a sealed copy; no plain email is in any column. *Source:* design LA-D7, LA-D11, §5. *Verified by:* database assertions after sign-up; the sealed value opens only with the key and the account id. *Evidence:* apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-03, -04, -05, -06: a right code for a new email gives a ticket; the details make the account, linked to the install, with the email sealed ; apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-06: the hash of the same address is the same for the same key and different for another, and is not a plain hash of the address
- [x] **LA-ACCOUNT-07** An install has at most one account: signing in to, or creating, a different account on an install that already has one is refused with `ALREADY_SIGNED_IN`; the same account again changes nothing. *Source:* design §4. *Verified by:* API tests. *Evidence:* apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-07: an install that already has an account is refused a different one (ALREADY_SIGNED_IN); the same one again changes nothing
- [x] **LA-ACCOUNT-08** If a ticket is valid but the email gained an account meanwhile, the install is linked to that account and the answer is `SIGNED_IN`; two creations at once make one account. *Source:* design §4. *Verified by:* API test with two concurrent creations. *Evidence:* apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-08: if the email gained an account after the code was checked, the ticket links the install to it and stores nothing it was told ; apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-08: two creations of one email at once make one account
- [x] **LA-ACCOUNT-09** Sign-out unlinks only this install; the account and its other installs are untouched. *Source:* ADR decision 6. *Verified by:* API test. *Evidence:* apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-09: signing out unlinks only this install; the account and its other installs stay
- [x] **LA-ACCOUNT-10** Deleting the account erases the email (hash and sealed copy), gender, birth year and consent record, and unlinks every install of the account; it answers 204 also when there is no account. Recognition rows stay. An audit row records the action without any personal value. *Source:* ADR decision 6. *Verified by:* API and database tests; a later sign-up with the same email makes a new account. *Evidence:* apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-10: deleting erases the email, gender, age and consent, unlinks every install, keeps the recognitions, and leaves an audit row with no personal value
- [x] **LA-ACCOUNT-11** `GET /api/v1/listener-account` returns whether the install is signed in and the email only in masked form (first character, stars, domain). *Source:* design §4. *Verified by:* API test: the response never holds the full address. *Evidence:* apps/api/test/listener-accounts.test.ts :: LA-ACCOUNT-11: reports whether the install is signed in and the email only masked, never the gender or age

## LA-STATS — who is listening

- [ ] **LA-STATS-01** The mix counts **distinct listeners** (one per account; one per install with no account) who identified the station's ads in the range, by gender and by age band, plus the number not known yet; a person with two installs counts once. *Source:* design §7. *Verified by:* API tests with seeded accounts, installs and recognitions.
- [ ] **LA-STATS-02** The age bands are under 18, 18–24, 25–34, 35–44, 45–54 and 55 and over, from the stored birth year at query time, with the boundary years tested. *Source:* design LA-D9. *Verified by:* API tests at each boundary.
- [ ] **LA-STATS-03** Small-group rule: below 10 known listeners no breakdown is returned; otherwise a group of 1–9 is merged into "Other groups", the smallest shown group joins when only one group would be hidden or the merged number is under 10, and a zero is shown as 0. *Source:* design LA-D10, §7. *Verified by:* unit tests of the rule at 9, 10 and 11 and for each case; an API test.
- [ ] **LA-STATS-04** There are two separate breakdowns and never a gender × age grid or any per-person row. *Source:* design LA-D10. *Verified by:* contract test of the response shape.
