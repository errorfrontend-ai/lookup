### Rollups

- [ ] **P7-ROLLUPS-01** Daily totals are kept in an ordinary rollup table, `daily_stats`, not in a materialized view (a materialized view cannot have row-level security). *Source:* slice-blueprint.md §10 (blueprint §2 line 19 "user analytics"; plan §Data model row daily_stats) [B333]; slice-plan-decisions-data-model.md §9k (plan §Data model row daily_stats, line 373) [D557]. *Verified by:* database catalogue test: `daily_stats` is a table, and no materialized view holds station statistics.
- [ ] **P7-ROLLUPS-02** A scheduled job rolls recognition events and engagement events up into `daily_stats` with an upsert (`INSERT … ON CONFLICT`), so running it twice over the same events gives the same rows. *Source:* slice-plan-cross-cutting.md §25 (plan §Phases row 7, line 651) [X554]. *Verified by:* database test: two runs over the same seeded events leave identical rows.
- [ ] **P7-ROLLUPS-03** Rollups are keyed on the station-local date of the capture time (`captured_at`), never the receipt time: a clip captured at 23:50 station time and received at 00:20 the next day is counted on the capture day. *Source:* slice-plan-cross-cutting.md §25 (plan §Phases row 7, line 651) [X555]; slice-plan-recognition.md §1 (plan §Recognition flow, time rule, line 471) [R50]. *Verified by:* rollup test with a station in `Africa/Lusaka`: an event captured at 23:50 and received at 00:20 the next day lands on the capture date; an event captured at 23:30 lands on that local date.
- [ ] **P7-ROLLUPS-04** Each rollup run re-aggregates the trailing 48 hours, so late deferred events are absorbed. *Source:* slice-plan-cross-cutting.md §25 (plan §Phases row 7, line 651) [X556]. *Verified by:* database test: an event inserted for yesterday after a run is counted after the next run.
- [ ] **P7-ROLLUPS-05** An event arriving 20 hours late is reflected after the next rollup run. *Source:* slice-plan-cross-cutting.md §25 (plan §Phases row 7, Verify, line 651) [X564]. *Verified by:* database test with a fake clock: insert an event captured 20 hours earlier, run the rollup, and the capture day's total includes it.
- [ ] **P7-ROLLUPS-06** Rollup totals equal the counts taken from the raw recognition and engagement events. *Source:* slice-plan-cross-cutting.md §25 (plan §Phases row 7, Verify, line 651) [X563]; slice-blueprint.md §10 ("rollups equal raw events") [B333]. *Verified by:* database test: for a seeded period, every total in `daily_stats` equals the matching count over the raw events.
- [ ] **P7-ROLLUPS-07** A forced failure of the rollup job is logged as one structured error line carrying the run's request id and the stack trace (the job runs through the wrapper of ALL-JOBS-01). *Source:* slice-plan-cross-cutting.md §25 (plan §Phases row 7, Verify, line 651) [X567]. *Verified by:* log-capture test: make the rollup throw; exactly one error line with the run's request id and the stack appears, and the scheduler keeps running.
- [ ] **P7-ROLLUPS-08** `daily_stats` is read-only for the API role: as `lookup_api`, `INSERT`, `UPDATE` and `DELETE` on it are refused; roll-up rows are written only by the roll-up job through a SECURITY DEFINER function (never through a table-level write grant to `lookup_api`), and station members and client viewers only read it under row-level security. *Source:* plan §Roles and RLS "Analytics : read-only for app_api; writes only via SECURITY DEFINER recog.* functions" (line 388); plan §Data model row daily_stats "Rollup table with RLS (materialized views can't have RLS)" (line 373). *Verified by:* privilege test: the three direct writes are denied as `lookup_api`; a roll-up run through the definer function writes rows; a catalogue test shows no table-level write grant on `daily_stats` to `lookup_api`.

## Possible gaps in the sources

Numbered once across the whole list; items above refer to these numbers.

### P7 — Analytics

1. **`daily_stats` has no column list.** Its dimensions (station, client, ad, campaign, action, hour, local date) and measures are not given anywhere, so "taps per button", "per hour" and "possible against resolved" cannot yet be checked against a schema. (slice-plan-decisions-data-model.md gap 17)
2. **The hour behind "per hour" is not defined.** The date rule says station-local date of `captured_at`; no source says the hourly counts use the same clock and time zone (the P5B Overview chart does say "in the station's time zone").
3. **No home for scheduled work.** The Render topology has no cron service, yet Phase 7 needs the rollup, and the system also needs partition creation (S1-SCALING-04), idempotency-key clean-up (P4-IDEMPOTENCY-19), expired-session clean-up and old-partition detaching. No source says what runs the scheduler or where `runJob` lives. (slice-plan-cross-cutting.md gap 6; checklist-1 gap 14)
4. **Late choices and the 48-hour window.** A chooser answered after the listener reconnects turns a "possible" into a "resolved". No source says what happens when that answer arrives after the trailing 48 hours have closed for that day.
5. **Weekly summary emails.** No content, recipient list, opt-out or phase is given (plan §E has no phase; the portal slice chose P7). (slice-plan-portal.md gap 17)
6. **The P5C client page before P7.** Review round 1 placed the client page's figures and CSV in P5C (conflict 2), so the page has working figures and a working CSV button from 5c; but the roll-ups they should come from arrive in P7, and no source says where the P5C numbers come from in between (part 4 gap 25).
7. **CSV details.** Who may export (station members as well as client viewers), the columns, the date range, and protection against spreadsheet formula injection (cells starting with `=`, `+`, `-` or `@`) are not stated. (slice-plan-portal.md gap 19)
8. **Overview numbers before P7.** The P5B Overview shows tiles and an hourly chart, but rollups arrive in P7; no source says where the Overview's numbers come from before then. (slice-plan-portal.md gap 7)
9. **Retention.** How long recognition events, engagement events, candidates and rollups are kept is not stated, which matters under the Zambia Data Protection Act. (slice-plan-decisions-data-model.md gap 23; slice-blueprint.md gap 10)
10. **Partitioning of the other traffic tables (resolved in review round 1).** The conventions do state the rule for every table that grows with listener traffic, so `engagement_events` and `recognition_candidates` are partitioned (ALL-SCALING-07, P4-DATABASE-03). Still open: each table's arrival-time column and the clean-up of the cross-month uniqueness table (part 2 gap 47). (slice-plan-decisions-data-model.md gap 22)
