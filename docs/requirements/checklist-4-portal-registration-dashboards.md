## Possible gaps in the sources (P5A, P5B, P5C)

### Sign-up and registration

1. **Who creates the station and the user at sign-up.** The built grants stop `lookup_api` creating stations or portal users directly (tested: "cannot create or delete stations directly", "cannot create or delete users directly"), and `lookup_admin_api` is for super-admin endpoints only. No source names the narrow function or role that sign-up uses to create the station, its first OWNER membership and the portal user.
2. **Where sign-up progress lives.** "Saved server-side after each step" has no table in the data model (data-model gap 19), and no source says how an applicant gets back in (signing in with the step-1 email and password, or a link), what ends `PENDING_VERIFICATION`, or whether step 4 can be submitted before both the phone and the email are verified.
3. **Email link.** How the email-verification token is stored (hashed?), how long it lasts, and how many times "Send the link again" may be used are not stated.
4. **Turnstile.** Whether Turnstile also guards code resend or sign-in, and what happens when Turnstile cannot be reached, are not stated.
5. **Abuse limits.** Apart from the per-address and per-account code limits, no source limits sign-up attempts per phone number, invitations sent, or ads created (each returns a presigned URL).
6. **Licence and logo formats.** Phones may produce PNG or HEIC photos of a licence; the plan allows only PDF and JPG. The logo's size and dimension limits, its output format and size after `sharp`, and how logos and header images are served (public path or signed links) are not stated.
7. **Review time.** "[2 working days]" is a placeholder; the number of resubmissions allowed is not stated.
8. **Password reset.** No plan or baseline text describes "forgot password" or a change-password screen, yet design S2-D7 schedules self-service reset (and the disable after 100 consecutive failed sign-ins) for Phase 5a. Review round 1 retired the two items that carried them (P5A-ACCOUNT-01, -02); they return as items only once the user confirms them. The flow, token lifetime, channel (SMS or email), rate limits, and that a reset revokes every session as a password change does (S2-SESSIONS-14), are not stated.
9. **Password length.** The SignupAccount wireframe's "At least 10 characters" conflicts with design S2-D5's 15-character minimum (chosen here); the wireframe needs updating.
10. **Wireframes missing.** The sign-up steps exist only at 375 px (the Design track asks for 1280 px too); there is no wireframe for the rejected state of the Application status page, the admin Stations, "Audio to check", "System health" and "Find by reference code" pages, or the admin console on a phone.

### Admin console

11. **SUPPORT role.** `platform_role` allows `SUPPORT`, but no source says what a support user may see or do.
12. **Two-factor details.** TOTP enrolment, storage of the secret (encrypted? column privileges?), recovery codes and lost-device recovery for super admins are not described.
13. **Admin write scope.** Which tables a super admin may write is defined only by the built grants ("policy USING (true)" in the plan); whether a super admin can create or pre-register a station (blueprint "tenant onboarding") is not stated.
14. **"Find by reference code".** What it searches (logs live in the log drain, not the database; recognition events; the audit trail) is not stated, and the short reference code shown in the app (for example "[7K2Q-9MXA]") has no stated mapping to the UUID request id.
15. **System health numbers.** The time window for match p95 and the error rate, what counts as an error, and whether the ingest worker has its own heartbeat tile are not stated.
16. **Overlap review decisions.** The actions a super admin can take on an overlap (keep separate, link, reject) and their effect on the stations' ads are not stated. Review round 1 moved the findings table into P5A (P5A-OVERLAP-REVIEW-04) so the page can be tested against seeded findings; the detection that fills it is still P8, and how the admin role reads the fingerprint schema awaits the user's decision (part 2 gap 48).
17. **Suspension details.** Whether members of a suspended station can still sign in and what they see, and whether a suspended station's own ads keep reaching listeners as a default card or not at all (recognition gap 16), are not stated.
18. **Re-review of an approved station (O2).** Whether its live ads keep reaching listeners while it is back in `PENDING_REVIEW`, where the proposed new name, frequency or licence is held until approved, whether the station is warned before saving such an edit, and how a time-zone change affects existing windows are not stated.
19. **"Report this".** Baseline §5 row 3 puts "'Report this' on every card" in phase 5a, but no source defines a report endpoint, storage, rate limit, or an admin screen where reports are read.
20. **Critical alerts.** The SMS "critical alerts" are not listed (which events, which recipients). Retry counts and back-off for the `notify` queue, the SMS sender id, and whether team invitations also go by SMS are not stated.
21. **Duplicate guard wording.** The plan flags a match with "an existing station"; the wireframe pill says "an approved station". The intended set (all stations, or approved only) needs confirming.

### Team and client viewers

22. **Team rules.** Whether the last OWNER can be removed or leave, whether an OWNER can change a member's role, how MANAGER differs from OWNER beyond team management (for example station-profile edits), and what happens when an invitee already has an account are not stated. The invitation lifetime is not given. There is no Team wireframe.
23. **Invitations table.** The plan gives only `token_hash`, `expires_at`, target and `invited_by`: no invited email or phone, no accepted or revoked marker, no single-use rule, no station or client reference (data-model gap 17).
24. **Client-viewer life cycle.** Who at a station may invite a client viewer (OWNER only, or MANAGER too), how a viewer accepts (sets a password or links an existing login), and how a station revokes a viewer are not stated.
25. **Client-viewer numbers before Phase 7.** The client page's figures and the CSV are listed in Phase 5c, but the roll-ups they should come from are Phase 7; where the numbers come from in between is not stated (conflict 2).
26. **CSV contents.** The CSV's columns and date range are not stated, and no source mentions protecting it against spreadsheet formula injection (cells starting with `=`, `+`, `-` or `@`).
27. **Card preview on the client page.** The plan requires a card preview for each ad; the ClientView wireframe omits it. There is no desktop wireframe of the client view.

### Station dashboard

28. **Overview numbers.** What the date-range select changes, given tiles labelled "today" and "7 days", and where the Overview's and the Clients page's numbers come from before the Phase 7 roll-ups, are not stated. "Caps nearly reached" has no threshold.
29. **Ads-list tab rules.** The "Needs attention" tab's criteria, which tab shows Paused ads, whether archived ads appear in any tab, the exact meaning of "Scheduled" (future period, or active but outside a window now) and of the "This month" filter (campaign overlaps the month, or created this month) are not stated.
30. **Row actions.** What "Duplicate" copies (client, audio, card, schedule), whether "Archive" pauses or ends a running campaign and whether it can be undone, what "Edit" opens, and what the "Extend" action opens are not stated. Whether the phone list has row selection, bulk actions and paging is not stated (the phone wireframe shows none).
31. **Polling numbers.** The back-off steps and the maximum interval of the 5-second poll are not given.
32. **Badge wording and a possible leak.** The Overview wireframe explains "Being checked" as "Part of this audio matches another ad — our team is reviewing it", which may tell a station that another (possibly competing) station's ad contains its audio, in tension with O6 and the rule that a station never learns of another station's upload.
33. **Weekly grid limits.** The desktop grid covers only whole hours from 05:00 to 23:00, while the phone editor accepts any minute and windows may cross midnight. How a 07:30 start or a 23:00–02:00 window is shown and edited on desktop, and whether the phone editor can express different hours on different days, are not stated.
34. **Grace wording.** The AdDetail wireframe says grace applies "after each slot"; the plan says "± grace" and part 2 chose both sides. The labels and help texts need the user's confirmation.
35. **Offer title and accent colour.** The "Offer title" field (60 characters) appears only in the NewAdButtons wireframe; whether it is the ad's title or a card field, and whether the card schema limits it, are not stated. The accent colour has no field in the built card contract, and its contrast threshold, the background it is checked against and its dark-mode use are not stated.
36. **Keyboard alternatives.** No keyboard alternative for drag-to-reorder buttons and no keyboard pattern for the 126-cell schedule grid (for example `role="grid"` with arrow keys) are stated.
37. **Touch targets below 44 px in the wireframes.** Bulk-bar buttons and the Chart/Table and 320/411 switches (36 px), table Play and More buttons, Previous/Next and "Open full size" (40 px), "Needs attention" action links (32 px), table checkboxes (20 px) and weekly-grid cells (20 px tall) are drawn smaller than the plan's 44 px; whether desktop-only controls are exempt is not stated.
38. **Palette.** Plan §Mobile D asks for "a restrained blue/neutral palette"; the wireframes and `tokens.json` use a warm neutral with a copper accent (`#A8431A`), and memory/look-up-wireframes.md says to keep those two in sync. Which the portal ships with, and whether the portal supports the dark colours in `tokens.json`, are not decided.
39. **Session expiry mid-task.** What the portal does when the 15-minute access cookie expires during the wizard (silent refresh, return to Sign in, keeping unsaved input) is not stated.
40. **Station profile against the built grants.** The built column grants forbid `lookup_api` editing name and frequency (S1-PRIVILEGES-20), while the plan lets the station edit them with re-review; the narrow function chosen in conflict 9 is not named in any source. Whether editing the contact phone requires verifying it again is not stated.
41. **Database work not listed.** The built `stations` table has no licence, contact, coverage, stream, verification or review columns; `client_viewers` and `invitations` do not exist; `clients` has no contact column; header-image variants have no storage columns. No source lists the Phase 5a, 5b and 5c migrations.
42. **Open decisions.** O2, O5, O6 and O16 are recommendations in the plan; no source records the user confirming each, and O5 (what the Independent Broadcasting Authority publishes) and O16 (Zambia coverage, sender-ID rules and price) still have their verification steps open.
43. **Client-viewer policies on tables without `client_id`.** The plan's client-viewer policy reads `client_id = ANY(app.client_ids())`, but in its data model `campaigns`, `campaign_windows` and `daily_stats` have no `client_id`. Whether each gets a policy that joins through `ads.client_id` or a `client_id` column of its own (with a composite foreign key) is not decided (P5C-DATABASE-04).
44. **Header-image upload limits.** The size limit, accepted types and presigned-address lifetime for card header images are not stated (P5B-CARD-BUILDER-10, -11); gap 6 covers the same for logos.
45. **Where a client's logo is set.** The plan gives clients a `logo_key` and shows the client's logo in lists and headers, but no screen or endpoint for setting it is named (P5B-CLIENTS-04).
